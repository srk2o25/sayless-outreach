# n8n — Standards

Workflows are authored visually in the n8n UI, then exported to `workflows/*.json` and committed — the UI is the editor, the JSON in this repo is the source of truth for what's deployed.

## Conventions

- **Export after every change.** From the n8n UI: workflow menu → Download. Overwrite the matching file in `workflows/`. A workflow that only exists in the running n8n instance and not in this folder is not considered shipped.
- **Caps and credentials are env vars, referenced by expression, never hardcoded into a node.** `LI_DAILY_CONNECT_CAP`, `BREVO_API_KEY`, etc. come from `docker-compose.yml` environment — a workflow node reads `{{$env.LI_DAILY_CONNECT_CAP}}`, it does not contain the number `18` typed into a filter condition.
- **The sequence lives in Postgres, not in the workflow graph.** `daily-scheduler` queries `sequence_steps` to decide what runs next for a prospect — it does not have one branch per step hardcoded. Adding a 7th step should never require editing this workflow.
- **A reply halts everything.** Any workflow that records an `event_type = 'replied'` row must, in the same execution, set `prospects.halted = true`. No other workflow may dispatch an action for a halted prospect — `daily-scheduler`'s query excludes them at the source. **Not yet reachable in practice**: nothing currently produces a `replied` event — see `email-events.json`'s note below on why email replies aren't detected, and LinkedIn replies aren't handled by any workflow yet either.
- **`trigger_type`/`event_condition` on a step are informational only — they don't gate scheduling.** Originally an `event`-trigger step (e.g. "LI message" on `on_accept`) only became due once its matching event existed. Since nothing detects a LinkedIn accept/reply (previous bullet), that dependency meant those steps never fired in practice — every prospect got permanently stuck on the first event-trigger step. Removed: `daily-scheduler`'s due-check now treats every step identically, purely by elapsed `delay_value`/`delay_unit` since the prospect's last event (or `created_at`). A step still shows its `trigger_type`/`event_condition` in `admin-ui` as a label of intent, but what actually fires it is the timer, chained off the previous step's real dispatch time — see the table below.

## The four pipeline workflows

All four built and verified (see git history) — `daily-scheduler`'s dispatch and `email-send`'s live send couldn't be verified against a real LinkedIn session / Brevo key (neither exists yet outside this dev environment), so verification there is request-shape and failure-path only, not a live send.

| File | Trigger | Responsibility |
|---|---|---|
| `daily-scheduler.json` | Cron, hourly (`Hourly Trigger`, on the hour), plus manual "Execute workflow" | Skips prospects sitting on a disabled step forward to the next enabled one, reads prospects due for their next step (every step — `time` or `event` trigger alike — checked against `(delay_value \|\| ' ' \|\| delay_unit)::interval` since the last event or `created_at`, see `sequence_steps.delay_value`/`delay_unit`, not a single `INTERVAL` column, per `db/CLAUDE.md`), applies `LI_DAILY_CONNECT_CAP` / `LI_DAILY_VISIT_CAP` / `EMAIL_DAILY_CAP_PER_INBOX` in-memory across the batch, dispatches each survivor to `linkedin-dispatch` or `email-send`. Despite the filename, this no longer runs once a day — the cadence moved to hourly so a step's delay actually gets honored within the hour instead of only being checked once at 8am; the name stayed to avoid a wider rename across this doc, the workflow id, and `daily-scheduler-run-now.json`. |
| `linkedin-dispatch.json` | Called by `daily-scheduler` | One HTTP call to `linkedin-worker`'s matching `/actions/*` endpoint per prospect, writes the result to `events` as `sent`/`skipped`, then always advances `current_step_id` to the next step regardless of outcome — a failed action no longer leaves a prospect stuck retrying the same step forever, it just gets logged as `skipped` and the sequence proceeds on schedule |
| `email-send.json` | Called by `daily-scheduler` | HTTP call to Brevo's transactional send API (tagged with `prospect:<id>` / `step:<id>` so `email-events` can map a later webhook callback back to it), writes `sent`/`skipped` to `events`, always advances `current_step_id` regardless of outcome — same reasoning as `linkedin-dispatch.json` above |
| `email-events.json` | Webhook, from Brevo | Receives Brevo's transactional webhook (open/click/bounce), maps it to `events` using the `tags` set at send time. **Does not detect replies** — Brevo's standard transactional webhook has no native reply event; that needs a separate inbound-email-parsing setup that doesn't exist yet. The `on_reply` / `halted = true` behavior described elsewhere in this repo is not wired up by this workflow today. |

## The admin CRUD workflows

Not in the original spec — added because `admin-ui`'s services already call these endpoints and, per `admin-ui/CLAUDE.md`, n8n is the only allowed API surface (no direct Postgres access from the browser, no separate backend). One webhook trigger per workflow — see implementation note below on why.

| File | Endpoint | Responsibility |
|---|---|---|
| `admin-list-campaigns.json` | `GET /campaigns` | Lists all campaigns |
| `admin-upload-campaign.json` | `POST /campaigns/upload` | Parses the uploaded CSV/XLSX, inserts the campaign (recording `templateCategoryId`), clones the default `sequence_steps` template onto it, applies the chosen template category's content onto those cloned steps ("Apply Template Content" node), bulk-inserts prospects |
| `admin-delete-campaign.json` | `POST /campaigns/delete` | Hard `DELETE FROM campaigns` — cascades to that campaign's `sequence_steps`, `prospects`, and `events` via existing FKs (see `db/CLAUDE.md`'s note on `events.step_id`'s cascade). Unlike prospects (soft-deleted via `archived`), campaigns have no soft-delete column — this is genuinely irreversible, and admin-ui confirms before calling it |
| `admin-list-prospects.json` | `GET /prospects?campaignId=[&includeArchived=true]` | Lists prospects for a campaign; excludes `archived` rows by default |
| `admin-update-prospect.json` | `PUT /prospects` | Updates one prospect's editable fields plus `halted`/`archived` (`id` in the body — same idiom as `admin-update-step`). Archiving *is* the "delete" action here — no hard `DELETE`, see `db/CLAUDE.md` |
| `admin-list-steps.json` | `GET /sequence-steps[?campaignId=]` | Lists steps (default template when `campaignId` omitted) |
| `admin-update-step.json` | `PUT /sequence-steps` | Updates one step (`id` in the body, not the URL — see note below) |
| `admin-reorder-steps.json` | `POST /sequence-steps/reorder` | Rewrites `step_order` for a list of step ids |
| `admin-linkedin-connection-status.json` | `GET /linkedin-connection-status` | Reads the single-row `linkedin_connection_status` table, for admin-ui's status pill |
| `linkedin-connection-mark-connected.json` | `POST /linkedin-connection/mark-connected` | Called by `linkedin-worker` itself (not admin-ui) right after a successful Connect flow captures a session — see `admin-ui/CLAUDE.md`'s documented exception for why admin-ui's *live* connect goes straight to `linkedin-worker` over a WebSocket instead of through here |
| `linkedin-connection-disconnect.json` | `POST /linkedin-connection/disconnect` | Called by admin-ui's "Disconnect" button (normal n8n path, not the WS exception) — calls `linkedin-worker`'s `/actions/disconnect` (deletes the session file) then marks `linkedin_connection_status` disconnected |
| `auth-login.json` | `POST /auth/login` | Verifies `{email, password}` against `users.password_hash` (salted `scrypt`, via Node's built-in `crypto` inside a Code node — see the `NODE_FUNCTION_ALLOW_BUILTIN` gotcha below), issues a token and inserts a `sessions` row on success. **This is the only workflow any auth exists in** — no other workflow checks the token admin-ui sends. See `docs/product-notes.md` for why that's a deliberate scope cut, not an oversight. |
| `admin-list-template-categories.json` | `GET /template-categories` | Lists all template categories |
| `admin-create-template-category.json` | `POST /template-categories` | Inserts a category, then auto-inserts its 3 blank template rows (`li_message`/`email`/`email_followup`) — admin-ui never "adds a template," only fills in the 3 slots every category always has |
| `admin-delete-template-category.json` | `POST /template-categories/delete` | Hard `DELETE` — cascades to its `templates`; campaigns that used it get `template_category_id` set `NULL`, not deleted |
| `admin-list-templates.json` | `GET /templates?categoryId=` | Lists the 3 templates for one category |
| `admin-update-template.json` | `PUT /templates` | Updates one template's `subject`/`bodyTemplate` (`id` in the body, same idiom as `admin-update-step`) |
| `email-accounts-status.json` | `GET /email-accounts` | Read-only: returns the configured Brevo sender (`BREVO_SENDER_EMAIL`/`NAME` env vars) plus today's send count, for admin-ui's Email Accounts card. No connect/remove action — actually connecting a mailbox is Brevo's own domain/API-key setup, not something this endpoint manages. |
| `daily-scheduler-run-now.json` | `POST /daily-scheduler/run` | Manually fires the exact same dispatch logic `daily-scheduler.json`'s hourly cron runs, for admin-ui's "Run pipeline now" button. **Deliberately a separate, standalone workflow** — duplicates `daily-scheduler`'s node chain rather than adding a second (Webhook) trigger onto the production cron workflow, after that combination proved unreliable in testing (see the gotcha below). admin-ui never reads this endpoint's response body — see why below. |
| `admin-prospect-timeline.json` | `GET /prospect-timeline?prospectId=` | Backs admin-ui's prospect detail modal (click a row in the Prospects table). One query aggregates the prospect's campaign's enabled `sequence_steps` and all of the prospect's `events` as JSON; a Code node walks the steps in order, marking each `completed`/`skipped` (there's a real `sent`/`skipped` dispatch event for it) or `pending`/`upcoming` (projects a `dueAt` by chaining `delay_value`/`delay_unit` forward from the last real event, matching `daily-scheduler`'s own due-check exactly). Only `sent`/`skipped` events count as a step's dispatch record — a step can also pick up a later, unrelated event (e.g. a manually-recorded `accepted`) that's newer but isn't the outcome of that step's own action. |

### Implementation notes for this n8n build (2.29.x)

Discovered the hard way while building the workflows above — worth knowing before adding more:

- **One webhook trigger per workflow, not several.** Multiple `Webhook` nodes sharing one workflow registered malformed paths in testing. Give each endpoint its own workflow.
- **Every `Webhook` node needs an explicit `webhookId` (a UUID) set on the node itself**, not just in `parameters`. Without it, this build registers the webhook at `<workflowId>/<node name>/<path>` instead of the plain configured path, and it never matches an incoming request.
- **Avoid `:param` route segments** if the frontend needs a stable URL — dynamic paths route through a different lookup that expects the node's `webhookId` UUID embedded in the URL (`/webhook/<uuid>/resource/:id`). Prefer a static path with the id as a query param or body field instead (see `admin-list-prospects` and `admin-update-step`).
- **Postgres node `queryReplacement`: always use the array form**, `={{ [expr1, expr2, ...] }}`, never the comma-joined string form (`={{expr1}},{{expr2}}`). The string form breaks whenever a value is `null` or resolves to an empty string — n8n treats an empty resolved string as "zero parameters supplied" and Postgres then errors with `there is no parameter $1`.
- Workflows are activated via a **Publish** button (versioned publish pipeline), not a simple Active toggle. After importing or re-importing a workflow via `n8n import:workflow`, it still needs a manual Publish, and n8n needs a restart (`docker restart cadence-n8n-1`) to pick up newly published webhooks. **Publish can be done via the API instead of clicking through the UI**: `POST /api/v1/workflows/:id/activate` with header `X-N8N-API-KEY: <key>` (generate one in the n8n UI: Settings → n8n API) does exactly what the Publish button does — the plain `/rest/workflows/:id/activate` route needs a real n8n login session and doesn't accept the basic-auth credentials, so it's not usable this way.
- **A Postgres node that can return zero rows needs `alwaysOutputData: true`** (a top-level node property) **and** the following `respondToWebhook` node needs `respondWith: "json"` with `responseBody: "={{ $input.all().filter(i => Object.keys(i.json).length > 0).map(item => item.json) }}"` — not `respondWith: "allIncomingItems"`. Without `alwaysOutputData`, a zero-row query produces zero items and the Respond node never even runs, sending an empty HTTP body instead of `[]`, which crashes a JSON-parsing client (admin-ui hit this in `admin-list-prospects`/`admin-list-campaigns`/`admin-list-steps`).
- **Code nodes can't `require()` any built-in Node module by default** (`NODE_FUNCTION_ALLOW_BUILTIN` is empty unless set) — `auth-login.json`'s password verification needs `crypto`, added via `docker-compose.yml`'s `n8n` service environment, same "single-tenant internal tool" justification as `N8N_BLOCK_ENV_ACCESS_IN_NODE`.
- **Don't add a second (Webhook) trigger to an already-working cron workflow, even though n8n nominally supports multiple trigger types sharing one node graph.** Tried this on `daily-scheduler.json` to add a manual-run button; every execution reported `"status": "success"` with no error, but the actual HTTP response back to the caller was empty on every call after the first one following an n8n restart — confirmed via the executions API that the workflow logic itself was never at fault. Root cause not fully pinned down (ruled out: duplicate executions, Postgres connection exhaustion, the caller's `Authorization` header, call frequency/timing — an open n8n editor tab with a test listener on the workflow was one confirmed contributor, but closing it didn't fully resolve it either). Fixed by giving the manual-run path its own fully standalone workflow (`daily-scheduler-run-now.json`, own `Webhook` trigger only) instead of touching the production cron workflow — never modify `daily-scheduler.json`'s trigger to add another entry point; duplicate the node chain into a separate file instead.
- **Given the above, treat `daily-scheduler-run-now.json`'s response as unreliable — don't build any admin-ui feature that depends on reading its response body.** The underlying dispatch always actually runs correctly (verified repeatedly against the `events` table); only the HTTP confirmation is flaky. `BatchesService.runPipelineNow()` in admin-ui deliberately ignores the response entirely (fire-and-forget) for this reason.

## Local dev

n8n UI: `http://localhost:5678` (basic auth from `.env`). Postgres credentials for the n8n Postgres node are the same `db` service credentials — same instance as everything else in this repo, not a second database.
